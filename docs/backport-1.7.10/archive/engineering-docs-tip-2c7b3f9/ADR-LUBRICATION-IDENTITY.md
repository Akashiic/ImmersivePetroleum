# Forge 1.7.10 machine identity for timed lubrication

The target Forge17 TileEntity has no `getTileData()`. Its real source in `build/rfg/minecraft-src/java/net/minecraft/tileentity/TileEntity.java` reads coordinates and writes id/coordinates; IE `TileEntityIEBase` delegates its own known custom NBT and exposes no arbitrary persistent attachment API. Therefore adding an unconsumed tag through a temporary `writeToNBT/readFromNBT` roundtrip would not persist identity.

`LubricationWorldData` keeps a weak attachment from the actual TileEntity instance to a UUID. It adds that UUID to the corresponding serialized TileEntity compound during `ChunkDataEvent.Save`, and restores it from `ChunkDataEvent.Load` onto the already reconstructed TileEntity in the event's own `chunkTileEntityMap`. This requires the existing public static Events class on both FML's tick bus and Forge's event bus. No TileEntity subclass substitution, reflection, coremod or global tick scan is involved.

The ordering is verified in the actual target sources. `AnvilChunkLoader.saveChunk` posts Save after constructing the chunk NBT and before queuing it for disk. `ChunkIOProvider.callStage2` calls `loadEntities`, posts Load synchronously, then installs the chunk in the provider and calls `onChunkLoad`. Consequently the attachment handler accesses the event chunk directly; a world/provider tile lookup there could recursively request a chunk that is not installed yet. Native `ChunkProviderServer.loadChunk` routes existing Anvil chunks through this same stage2 path for synchronous and asynchronous callers. Fresh generated chunks have no attachment to restore.

A new machine instance at the same coordinates has no attachment and receives a different UUID upon a new authorized lubricant application. The previous application matches both position and UUID, so it cannot accelerate a replacement before or after a restart. Dormant chunks that preserve the same TileEntity object preserve its weak attachment; disk reconstruction recovers it through the saved UUID. Attachments retain neither a strong TileEntity reference nor a world reference. Handlers iterate only the TileEntities already present in a chunk being saved/loaded, without requesting chunks or doing worker-thread world calls.

Malformed attachment types, noncanonical UUIDs and conflicting load bindings cannot receive fresh authority. Their raw NBT remains attached for subsequent saves. A conflicting binding is wrapped in an invalid compound so another restart cannot reinterpret it as a valid UUID. Legacy/custom loaders which omit the Forge chunk-data events cannot recover a timer; the implementation fails closed instead of guessing identity from coordinates. Independently persisted chunk and WorldSavedData snapshots are not a transactional filesystem: an interrupted mismatched save can lose remaining duration, but a mismatched UUID cannot transfer the old timer to a new machine. No crash-atomic durability claim is made.

Four written domain tests cover UUID attachment roundtrip, replacement at identical coordinates, raw malformed preservation and conflicting binding across another reload. The dedicated lubrication campaign now verifies a real native Crusher attachment over the first restart, breaks/reforms it at the same position and rejects the old timer both immediately and across the following restart. Its write boot also invokes the parent-owned `DrillOilProbe.verify` before the lubrication fixture. These tests/campaign have not been run by this subtask; the parent coordinates the build and runtime gates.
